## Why

Onboarding promises **"Search photos with natural language"** (`src/screens/Onboarding/OnboardingScreen.tsx:49`), but today's search is purely lexical: `SearchService` runs a MiniSearch token index over `filename`/`labels`/`ocrText` (`src/services/search/SearchService.ts:28-39,122-148`). A query like *"day at the beach"* only matches photos whose labels/OCR literally contain those tokens — it cannot match a photo captioned *"kids building a sandcastle by the shore"*. Foundation #1 already shipped the storage for the fix — an `embeddings` table (`media_file_id`, `vector`, `dim`, `model_version`, `created_at`) at `src/services/database/schema.ts:104-113`, the `Embedding` model (`src/models/Embedding.ts`, registered `src/services/database/database.ts:33`) — but **nothing generates, indexes, or queries vectors**. This change closes that gap: it generates on-device text embeddings for each file's enrichment text, indexes them for cosine/kNN retrieval, and **augments** (does not replace) the lexical index with a hybrid re-rank, finally delivering the natural-language-search promise.

## What Changes

- **On-device embedding pass (new queued tier).** A new all-static `EmbeddingService` wraps `react-native-executorch@0.9.2`'s **non-React** `TextEmbeddingsModule.fromModelName(...)` (`node_modules/react-native-executorch/.../TextEmbeddingsModule.d.ts`; `forward(input): Promise<Float32Array>`), embedding each file's assembled searchable text (caption + description + labels + OCR + filename — the same fields `SearchService.addToIndex` already gathers, `SearchService.ts:83-96`). The vector is L2-normalized, base64-serialized, and written to the #1 `embeddings` table with its `dim` and `model_version`. **Model choice is POC/runtime-dependent** — the pinned `0.9.2` registry ships `all-minilm-l6-v2` (**384-dim**) and siblings but **no** EmbeddingGemma; the exact model/dim/`model_version` are flagged for POC tuning (see design).
- **Queued as `task_type = "embedding"`, drained by the #3 orchestrator.** Embedding work is enqueued as a `processing_queue` row with `task_type = "embedding"` — the token the archived `processing-queue-tiers` spec already reserves as an example (`openspec/specs/processing-queue-tiers/spec.md:7`). The orchestrator drains it as an **independent third stream** via the existing tier-agnostic `ProcessingQueueRepository.getNextPendingByTaskType` (`ProcessingQueueRepository.ts:104-118`), mirroring the Tier-0 drain (`OrchestratorService.processNext`, `OrchestratorService.ts:185-268`) — a Tier-1/embedding backlog never blocks Tier-0.
- **Gated by #5.** The embedding drain runs under `BackgroundTaskService`, inheriting #5's thermal pause axis for free (`BackgroundTaskService.shouldPauseProcessing`). Model **admission** is composed from #5's `DeviceCapabilityService`/`ThermalService` primitives; because a ~90 MB MiniLM is far lighter than Gemma's 3–4 GB, reusing `canRunTier1()` verbatim vs. a lighter `canRunEmbeddings()` floor is a **#5-composition decision flagged POC-dependent** (design D6).
- **Semantic vector index + query path.** A new all-static `SemanticSearchService` hydrates an **in-memory L2-normalized Float32 matrix** from the `embeddings` table (persisted to MMKV, updated incrementally per embed — mirroring `SearchService`'s index/serialize/load pattern, `SearchService.ts:41-75,166-194`). Query = embed the query string once, then a single cosine (= dot, since normalized) / kNN pass. **Recommend in-JS cosine over a native `sqlite-vec` layer** for the target library size, with sqlite-vec flagged as a documented escape hatch (design D5).
- **Hybrid lexical + semantic search (additive).** A new hybrid combiner fuses MiniSearch results with semantic results via **Reciprocal Rank Fusion** (robust to the two engines' incomparable score scales), returning one ranked `media_file_id` list to the existing consumers (`SearchModeOverlay.tsx:86`, `MainScreen.tsx:81`). `SearchService.search` stays byte-for-byte intact; hybrid is a new additive entry point that **degrades gracefully to lexical-only** when the vector cache/model is unavailable.

## Capabilities

### New Capabilities
- `semantic-embedding-generation`: the all-static `EmbeddingService` + the queued `embedding` pass — assemble a file's searchable text, embed it on-device via the executorch text-embeddings module (POC-flagged model), L2-normalize, base64-serialize, and persist to the #1 `embeddings` table with `dim`/`model_version`; idempotent and model-versioned (stale-vector re-embed), admission-gated via #5.
- `semantic-vector-search`: the vector store + retrieval — an in-memory L2-normalized Float32 matrix cache hydrated from the `embeddings` table and persisted to MMKV, upserted incrementally per embed, exposing a `SemanticSearchService.search(queryText)` cosine/kNN path; the storage recommendation (in-JS vs. sqlite-vec) with tradeoffs.
- `hybrid-search`: the lexical+semantic fusion surface — a Reciprocal-Rank-Fusion combiner that augments MiniSearch with the semantic ranker into one ranked result set, additive to `SearchService` (existing lexical API unchanged), degrading to lexical-only when embeddings are absent — fulfilling the onboarding natural-language-search promise.

### Modified Capabilities
- `processing-orchestrator`: the existing **"Selection is tier-aware and forward-compatible"** requirement is extended so the orchestrator concretely drains the `embedding` stream as an independent third tier (enqueued after enrichment persist, gated by #5), instead of `tier0_mlkit` being the only drained stream. No other orchestrator requirement changes.

## Impact

- **New JS:** `src/services/ml/EmbeddingService.ts` (executorch text-embeddings wrapper, all-static), `src/services/search/SemanticSearchService.ts` (matrix cache + cosine/kNN), a hybrid combiner (extending `src/services/search/SearchService.ts` or a sibling), shared searchable-text assembly extracted from `SearchService.addToIndex`; new `STORAGE_KEYS.SEMANTIC_INDEX` and an `EMBEDDING_TASK_TYPE` constant; a new `EmbeddingRepository` (the `embeddings` table has a model but no repository yet).
- **Edited JS:** `src/services/orchestrator/OrchestratorService.ts` (enqueue an `embedding` row post-persist; drain the `embedding` stream in a tick, composed with the existing Tier-0 drain); search consumers (`SearchModeOverlay.tsx`, `MainScreen.tsx`) opt into the hybrid entry point.
- **Dependencies:** none added — `react-native-executorch@0.9.2` (already present, `package.json`) supplies the text-embeddings module/hook; `minisearch@^7.2.0`, `@nozbe/watermelondb`, `react-native-mmkv` already present. The embedding model's `.pte` + tokenizer are fetched at first run by the executorch resource fetcher (POC-sized).
- **Depends on:** **#1** (embeddings table + `caption`/`description` columns — verified in `schema.ts`) and **#7** (the on-device Gemma/executorch enrichment wave that integrates the executorch runtime — cf. #4 `executorch-runtime-bootstrap` — and populates `caption`/`description`/tags, the richest embedding inputs). Labels(`source=mlkit`)+OCR from Tier-0 are already embeddable today, so semantic search adds value even on Tier-0-only devices, but the natural-language quality bar tracks #7's enrichment.
- **POC gate inheritance:** every executorch-model assumption (that an embedding `.pte` loads and runs on-device) inherits #4's GO/NO-GO; latency/quality/output-dim are re-tuned after the on-device embedding POC (see design "POC-dependent" flags).
- **Conventions:** Biome (tabs, double quotes, `noExplicitAny: error`), strict TS, all-static services, legacy decorators, `@services`/`@models`/`@shared-types` aliases. New/edited JS stays typecheck- and lint-clean.
- **Verify (baseline-relative):** `tsc --noEmit` reports **8** pre-existing `TS6133` errors in 4 unrelated UI files; this change adds **zero** new typecheck errors (count stays 8), plus a Metro bundle check that the JS graph resolves.
