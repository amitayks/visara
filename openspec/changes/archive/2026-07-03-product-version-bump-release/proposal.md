## Why

This is the **"ship the new version" mechanic** for the ML-Kit → on-device-Gemma-4 migration: the release that packages the accumulated capability jump (a real multimodal AI engine), the raised OS/ABI floors (iOS **26.0**, Android **minSdk 36**, `arm64-v8a`-only), and hands the human a single, reproducible `npm run bump <x.y.z>` → reconcile → build-accept → release path. It exists now because the migration's predecessor changes (#7–#10) plus the #4/#6 on-device Gemma POC converge into one user-facing product bump, and the release tooling is **not** currently trustworthy: `bump-version.js` silently no-ops on iOS and crashes at the end. **This change fixes the mechanic, defines the release notes, and defines the version-file reconciliation + full-build acceptance so the release can actually go out — it does not itself decide GO** (that is the #4/#6 gate) and it does not tune Gemma.

## What Changes

- **Repair `npm run bump <x.y.z>` (`bump-version.js`) so it rewrites EVERY version anchor — today it does not.** Two verified defects:
  - **iOS section targets phantom paths.** `bump-version.js` §4/§5 write `ios/VisaraApp.xcodeproj/project.pbxproj`, `ios/VisaraApp/Info.plist`, `ios/VisaraAppTests/Info.plist` — **none exist**. The real project is `ios/Visara.xcodeproj/project.pbxproj` (+ `ios/Visara/Info.plist`). So `existsSync()` is false and iOS is **never bumped**: the pbxproj still reads `MARKETING_VERSION = 1.0` / `CURRENT_PROJECT_VERSION = 1` (`ios/Visara.xcodeproj/project.pbxproj:339,347,367,374`) while JS/Android are at `2.0.0`. **BREAKING drift, live in the app:** the Settings screen renders `DeviceInfo.getVersion()` (`src/screens/Settings/SettingsScreen.tsx:11` → `src/components/organisms/SettingsDrawer.tsx:378`), which shows **"Version 1.0" on iOS but "2.0.0" on Android** today.
  - **The script crashes after writing.** The final summary block (`bump-version.js` bottom) references `major`/`minor`/`patch`, but those are `const`-scoped **inside** each `try` (§3/§4/§5) → uncaught `ReferenceError` on every run, non-zero exit, and the "Next steps" never print. Files are written first, so the crash masks partial success.
- **Repoint iOS to `ios/Visara.xcodeproj/project.pbxproj` and `ios/Visara/Info.plist`, and hoist `[major, minor, patch]` to one module-scope parse.** The real `Info.plist` already defers to `$(MARKETING_VERSION)`/`$(CURRENT_PROJECT_VERSION)` (`ios/Visara/Info.plist:19-24`), so the pbxproj is the single iOS source of truth and §5's `includes("$(MARKETING_VERSION)")` guard correctly no-ops there — the only real iOS fix is the path.
- **Author a release-notes artifact** (what's-new copy for the on-device-AI jump + the raised-floor / dropped-device-support user impact), stored in a tracked repo location, per release.
- **Define a version-file reconciliation checklist** that proves every anchor agrees post-bump (`package.json`, `app.json`, `android/app/build.gradle` versionCode/versionName, iOS pbxproj `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION`), catches the fail-soft partial-bump case (the script `catch`es per section and continues), and asserts **build-number uniqueness** for repeat store uploads of one marketing version.
- **Verify the newest-only floors are reflected in store-metadata expectations** (App Store "Requires iOS 26.0"; Play `minSdk 36` / Android 16 + `arm64-v8a`-only device catalog + the multi-GB model-download data disclosure) — these are store-console expectations to reconcile, not files the script edits.
- **Define a final full-build acceptance gate:** iOS device + **arm64 iOS-26 Simulator (post-#8)** + Android flagship, all green, BASELINE-relative typecheck (8 pre-existing `TS6133`, zero NEW) + a Metro-bundle check + `npm run lint`.
- **Recommend the bump level and flag it as the human's call.** Given the wholesale engine replacement AND the dropped device support, this reads as **major → `3.0.0`** under semver; final choice (and the marketing narrative) is the human's.

## Capabilities

### New Capabilities
- `version-bump-mechanic`: `npm run bump <x.y.z>` deterministically rewrites all four platform anchors — `package.json`, `app.json`, Android `versionCode`/`versionName`, iOS `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` on the **real** `ios/Visara.xcodeproj` — with a documented `versionCode = major*10000 + minor*100 + patch` derivation, its constraints, and a clean exit.
- `release-notes-authoring`: a per-release, tracked release-notes document capturing the on-device-AI capability jump and the raised-floor user impact, in a form usable for App Store / Play "what's new" and the git tag.
- `version-file-reconciliation`: a checklist that proves every version anchor agrees after a bump, that the newest-only OS/ABI floors are reflected in store-metadata expectations, and that store build numbers are unique/monotonic for repeat uploads of a marketing version.
- `release-build-acceptance`: the final full-build acceptance gate (iOS device + arm64 iOS-26 Simulator [post-#8] + Android flagship) with baseline-relative typecheck, a Metro-bundle check, and lint, run only after the #4/#6 POC returns GO.

## Impact

- **Build tooling (repaired):** `bump-version.js` — iOS paths repointed to `ios/Visara.xcodeproj/project.pbxproj` + `ios/Visara/Info.plist`; `[major, minor, patch]` hoisted to module scope to end the trailing `ReferenceError`. No application/`src` code changes.
- **Version anchors (rewritten by the bump, per release):** `package.json:version`, `app.json:version`, `android/app/build.gradle:85-86` (`versionCode`/`versionName`; SDK floors at `android/build.gradle:4-6` are NOT version-bumped), `ios/Visara.xcodeproj/project.pbxproj` `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` (`:339,347,367,374`). `ios/Visara/Info.plist` is variable-driven and needs no edit.
- **Store-metadata expectations (reconciled, not edited by the script):** App Store min-OS 26.0; Play `minSdk 36` (Android 16) + `arm64-v8a`-only catalog + model-download data disclosure. No `fastlane`/`metadata/` directory exists in-repo today, so these are console-side reconciliation steps.
- **Doc anchor (out of band):** `README.md:215` hardcodes "v2.0.0"; the script does not touch docs — listed in the reconciliation checklist as an optional non-build anchor.
- **Sequencing / dependencies:** runs **last** in the migration wave, after predecessor changes #7–#10 are merged (#8 specifically unblocks the arm64 iOS-Simulator acceptance leg) and after the #4/#6 on-device Gemma POC returns **GO**. NO-GO ⇒ no release.
- **Conventions:** Biome (tabs, double quotes, `noExplicitAny: error`), strict TS; `bump-version.js` already emits tab-indented JSON + trailing newline (Biome-clean). Verify closes on `npm run typecheck` (baseline 8 `TS6133`, zero NEW) + Metro-bundle check + `npm run lint`.
- **POC-dependent (re-tune after #4/#6):** release-notes "what's new" copy, store data-safety/model-size disclosures, device-support claims (POC currently excludes iPhone from inference), and the acceptance latency budget — all depend on real POC output shape/latency/quality and on whether GO is reached at all.
