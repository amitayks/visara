## Why

The iOS **arm64 Simulator cannot build** while both GoogleMLKit and `react-native-executorch` are installed: every MLKit pod sets `EXCLUDED_ARCHS[sdk=iphonesimulator*] = arm64` (e.g. `ios/Pods/Target Support Files/GoogleMLKit/GoogleMLKit.debug.xcconfig:3`) because GoogleMLKit ships **no arm64-simulator slice**, while `react-native-executorch` sets `EXCLUDED_ARCHS[sdk=iphonesimulator*] = x86_64` (`ios/Pods/Target Support Files/react-native-executorch/react-native-executorch.debug.xcconfig:4`) because it ships **only** an arm64-sim slice. The two exclusions are mutually exclusive per simulator arch, so on an Apple-Silicon Mac **neither** simulator arch links, and the app-level empty override `"EXCLUDED_ARCHS[sdk=iphonesimulator*]" = ""` (`ios/Visara.xcodeproj/project.pbxproj:423,502`) cannot reconcile it. This blocks day-to-day iOS development for the entire Gemma-4 migration. Retiring GoogleMLKit is the single move that unblocks the arm64 simulator — and it is only possible now because `react-native-executorch@0.9.2` already ships dedicated on-device **OCR** (CRAFT detector + CRNN recognizer) and **image classification** (EfficientNet-V2-S) models that can take over the Tier-0 literal pass, with **Apple Vision** (`VNRecognizeTextRequest`) available as an iOS OCR fallback.

## What Changes

- **Swap the Tier-0 backend off GoogleMLKit onto executorch**, behind the existing `AnalysisEngine` seam. `MlKitEngine` (`src/services/ml/engines/MlKitEngine.ts`) keeps its `descriptor.id = "mlkit"` and its `Promise.all` two-producer structure **unchanged**; only the internals of `ImageLabelingService` (`src/services/ml/ImageLabelingService.ts`) and `TextRecognitionService` (`src/services/ml/TextRecognitionService.ts`) are rewritten to call `ClassificationModule` / `OCRModule` from `react-native-executorch` instead of `@react-native-ml-kit/*`. The #2 seam (`ProcessingService.processMedia`, `src/services/ml/ProcessingService.ts:43-45`) and #3 orchestrator stay untouched.
- **Add an iOS Apple-Vision OCR fallback** — a small native module (`VNRecognizeTextRequest`) modeled on the existing `ios/Visara/MediaObserver/MediaObserverModule.{swift,m}` pattern — that `TextRecognitionService` routes to on iOS when executorch OCR is unavailable or below the parity bar.
- **Add an OCR-parity gate**: a dev-only harness that captures the current ML Kit OCR baseline on a fixed image corpus **before** removal, then scores executorch OCR (and Apple Vision) against that baseline + ground truth, deciding GO vs. iOS-Vision-fallback. **BREAKING** intent: the Tier-0 label vocabulary changes (ML Kit generic labels → ImageNet-1k classes); labeling parity is best-effort, OCR parity is the hard gate.
- **Remove the ML Kit dependencies and pods**: drop `@react-native-ml-kit/image-labeling` + `@react-native-ml-kit/text-recognition` from `package.json`; `pod install` regenerates the Pods without the ~106 `GoogleMLKit`/`MLKit*`/`MLImage` lines and the two `RNMLKit*` pods (`ios/Podfile.lock:2751,2754`), which also strips all MLKit framework/lib/header propagation from the aggregate `ios/Pods/Target Support Files/Pods-Visara/Pods-Visara.*.xcconfig`.
- **Reconcile the arm64-simulator arch settings**: replace the app-level `"EXCLUDED_ARCHS[sdk=iphonesimulator*]" = ""` at `project.pbxproj:423,502` with `x86_64` (mirroring executorch's arm64-sim-only slice), so a simulator build cleanly targets arm64 only. Keep static linking and the fmt-consteval `post_install` patch (`ios/Podfile:12-16,33-60`).
- **Acceptance**: an agent-run **arm64 iOS/iPadOS 26 Simulator build + install + launch smoke** — now finally achievable with GoogleMLKit gone — plus a Tier-0 OCR/classification `forward()` data point on the sim (the executorch OCR/classification `.pte`s are XNNPACK/**CPU**, unlike the MLX-only Gemma LLM, so on-sim Tier-0 inference is expected to run).

## Capabilities

### New Capabilities
- `tier0-executorch-engine`: the Tier-0 OCR + labeling pass runs on `react-native-executorch`'s `OCRModule` (CRAFT+CRNN) and `ClassificationModule` (EfficientNet-V2-S) behind the unchanged `MlKitEngine`/`Promise.all` seam — lazy one-time model load/memoization, output-shape adaptation to the existing `ProcessingResult`, `isAvailable` guard, resolve-not-reject preserved.
- `apple-vision-ocr-fallback`: an iOS-only native module wrapping `VNRecognizeTextRequest`, plus the `TextRecognitionService` branch that uses it when executorch OCR is unavailable or under the parity bar on iOS.
- `ocr-parity-gate`: the parity harness + criteria that compare executorch OCR (and Apple Vision) against a pre-removal ML Kit baseline and ground truth, gating the swap and selecting the iOS fallback.
- `googlemlkit-retirement-arm64-simulator`: removal of the two `@react-native-ml-kit` npm packages and the GoogleMLKit/MLKit pods, the `pod install` regeneration, the `EXCLUDED_ARCHS` reconcile in `project.pbxproj`, and the arm64-simulator build/install/launch smoke acceptance.

### Modified Capabilities
- `mlkit-analysis-engine`: the two ML-Kit-specific requirements ("reproduces the current pass byte-for-byte", "adds no dependency and no native code") are removed — the Tier-0 backend is now executorch (a native dependency) with an iOS Vision fallback; the stable-contract requirements (descriptor `id="mlkit"`, resolve-with-fallback on failure) are retained and re-homed into `tier0-executorch-engine`.

## Impact

- **Dependencies removed:** `@react-native-ml-kit/image-labeling ^2.0.0`, `@react-native-ml-kit/text-recognition ^2.0.0` (`package.json`). Transitively removes `GoogleMLKit`, `MLKitCommon/Vision/VisionKit/ImageLabeling*/TextRecognition*(+Chinese/Devanagari/Japanese/Korean)`, `MLImage`, and (if otherwise unreferenced) `GoogleDataTransport`, `GoogleUtilities`, `GoogleToolboxForMac`, `GTMSessionFetcher`, `PromisesObjC`, `nanopb`, `Protobuf`.
- **Dependencies reused (already installed):** `react-native-executorch 0.9.2` + `react-native-executorch-bare-resource-fetcher` (added by the executorch-runtime-bootstrap change). No new npm dependency is introduced by this change.
- **iOS native (edited/new):** `ios/Visara.xcodeproj/project.pbxproj:423,502` (`EXCLUDED_ARCHS[sim]` `"" → x86_64`); regenerated `ios/Podfile.lock` + `ios/Pods/**` after `pod install`; new `ios/Visara/VisionOCR/VisionTextRecognizer{Module.swift,Module.m}` (Apple Vision). Static linking and the fmt patch preserved (`ios/Podfile:12-16,33-60`).
- **JS (edited/new):** `src/services/ml/ImageLabelingService.ts` + `src/services/ml/TextRecognitionService.ts` internals rewritten; new `src/native-modules/NativeVisionTextRecognizer.ts` (iOS) using the `@native-modules` alias; a dev-only parity-harness module. `MlKitEngine`, `EngineRegistry`, `ProcessingService`, and `AnalysisEngine` are **not** modified.
- **Provenance unchanged (deliberate):** `descriptor.id` stays `"mlkit"`, so `labels.source = "mlkit"` (`src/services/database/MediaFileRepository.ts:272,337`), `ai_model_version = "mlkit"` (`:50`), `processing_queue.task_type = "tier0_mlkit"` (`src/services/orchestrator/OrchestratorService.ts:22`), and the `migrations.ts:54` backfill all remain valid; the `label-provenance`, schema, and orchestrator specs are untouched.
- **Behavioral change:** Tier-0 now has a first-run model download (CRAFT + CRNN + EfficientNet `.pte`s, tens of MB) and an async load, versus ML Kit's always-ready bundled models; and the label vocabulary shifts to ImageNet-1k. Both are POC-gated for latency/quality/thresholds.
- **Conventions:** Biome (tabs, double quotes, `noExplicitAny: error`), strict TS, all-static services, `@services`/`@models`/`@shared-types`/`@native-modules` aliases. Verification: `npm run typecheck` (baseline 8 pre-existing TS6133; zero NEW), a Metro-bundle check, and `npm run lint`.
- **Depends on:** #2 `ml-engine-interface-seam` (archived) and #4 `executorch-runtime-bootstrap` (in-flight GO/NO-GO gate). This change also *unblocks* #4's own arm64-simulator smoke, which GoogleMLKit currently prevents.
