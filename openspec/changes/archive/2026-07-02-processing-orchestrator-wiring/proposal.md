## Why

Visara's on-device processing pipeline is fully **scaffolded but never wired together** — the parts exist, the connective orchestrator does not. Verified by grep: `ProcessingService.processMedia` has no external caller (only the unused internal `processQueue` loop at `ProcessingService.ts:71`); `ProcessingService.addToQueue`/`processQueue`/`clearQueue` have **zero** call sites; `ProcessingQueueRepository` (the repo-backed, restart-survivable queue) has **zero** call sites; `MediaFileRepository.createWithProcessingResult`/`updateWithProcessingResult` (the only writers of labels/ocr) have **zero** call sites (`MediaFileRepository.ts:173,226`); `BackgroundTaskService.start`/`initialize` have **zero** external callers; `MediaDiscoveryService` is imported into onboarding but every use is commented out (`OnboardingScreen.tsx:368`, producing the baseline `TS6133` dead-import error); and `GalleryContext`'s `SET_MEDIA_FILES` action is **never dispatched** (`GalleryContext.tsx:32,61`). Change #1 made the schema Gemma-ready and change #2 made the analysis producer a swappable engine, but nothing discovers media, enqueues it, drives the queue, persists results, updates search, or populates the gallery. This change **builds the missing orchestrator** that connects those pieces end to end using only existing parts — no Gemma, no native code, no new dependency.

## What Changes

- **New `OrchestratorService`** (`src/services/orchestrator/OrchestratorService.ts`, all-static per repo convention): the connective hub that runs discovery (`MediaDiscoveryService`) → upsert `media_files` rows → enqueue via `ProcessingQueueRepository` with `task_type = "tier0_mlkit"` → drain each item through `ProcessingService.processMedia` (the change-#2 engine seam; Tier-0 `MlKitEngine` today) → persist via `MediaFileRepository.updateWithProcessingResult` → **incrementally** update `SearchService` (`addToIndex`, not full `index()` rebuild) → emit progress events → drive gallery population. Exposes a framework-agnostic `subscribe()` observer API.
- **Drive the REPO-BACKED queue via `BackgroundTaskService`**, reusing its pause/resume, battery + night gating, and MMKV checkpoint (`BackgroundTaskService.ts:100,309,339`). The orchestrator's per-tick function drains one persistent `ProcessingQueueRepository` item; the durable queue (not volatile memory) is the single source of truth, giving stop/resume across app kills.
- **Reconcile the two queue notions:** `ProcessingService`'s in-memory queue (`ProcessingService.ts:16-112`) is **deprecated and bypassed** (JSDoc `@deprecated`, no runtime use); `ProcessingService` is used only as the stateless engine seam (`processMedia`/`getEngine`/`setEngine`). Retry/priority/state now live in the persistent `ProcessingQueueRepository` (which already has `retryCount`/`markAsFailed`/`retry`/priority ordering).
- **Close two persistence wiring gaps** so idempotency/resumability actually work: `ProcessingQueueRepository.create` learns `taskType`/`modelVersion` (today it sets neither, so enqueues would violate the `processing-queue-tiers` contract) plus a tier-filtered `getNextPendingByTaskType` and a stale-`processing`→`pending` crash-recovery helper; `MediaFileRepository` writers stamp `processed_at`/`ai_model_version`/`ai_schema_version` (today they set only `is_processed`, breaking change #1's `is_processed === (processed_at !== null)` invariant) and gain an upsert-by-uri path.
- **Bridge the static orchestrator to React state** (`src/components/system/OrchestratorBridge.tsx`, mounted once in `App.tsx`): maps orchestrator progress events → `ProcessingContext` dispatches (`START_PROCESSING`/`UPDATE_PROGRESS`/`ADD_FAILED_FILE`/`SET_PAUSED`/`STOP_PROCESSING`); drives `GalleryContext` `SET_MEDIA_FILES` from `MediaFileRepository.observeVisible()`; folds live `MediaObserver` `ContentObserver` changes in via `OrchestratorService.enqueueDiscovered`; propagates `SettingsContext` battery/night toggles to `BackgroundTaskService.updateSettings`.
- **Tier-aware and forward-compatible:** Tier-0 only now, but `task_type`/`model_version` selection, an engine-per-tier map over the change-#2 `EngineRegistry`, and a version-aware idempotency key leave clean seams for Tier-1 (Gemma) selection, capability/thermal gating (change #5), and model-version-aware reprocessing (change #10) to layer on **without a rewrite**.
- **No** Gemma, **no** native code, **no** new npm dependency — pure wiring of existing pieces. NOT breaking.

## Capabilities

### New Capabilities
- `processing-orchestrator`: an all-static `OrchestratorService` that connects discovery → upsert → enqueue → analyze → persist → search → progress → gallery into one resumable, idempotent, tier-aware pass, with a defined trigger model (post-onboarding foreground scan + background continuation) and a framework-agnostic event API.
- `queue-drive-and-gating`: driving the persistent `ProcessingQueueRepository` through `BackgroundTaskService` (pause/resume, battery + night gating, MMKV checkpoint) as the single source of truth, deprecating/bypassing `ProcessingService`'s in-memory queue, with tier-aware enqueue (`task_type`)/selection and crash recovery of stranded `processing` rows.
- `pipeline-persistence-and-search`: Tier-0 completion stamps `processed_at`/`ai_model_version`/`ai_schema_version` so change #1's invariant holds and re-runs are idempotent, and search is updated **incrementally** via `SearchService.addToIndex` per processed file instead of a full rebuild.
- `orchestrator-gallery-bridge`: a React boundary that maps orchestrator progress events to `ProcessingContext` and drives `GalleryContext` `SET_MEDIA_FILES` from `observeVisible()`, folds live `MediaObserver` changes in via `enqueueDiscovered`, and propagates battery/night settings to `BackgroundTaskService`.

## Impact

- **Code (new):** `src/services/orchestrator/OrchestratorService.ts` (the hub, under the existing `@services/*` alias); `src/components/system/OrchestratorBridge.tsx` (the React wiring, under `@components/*`).
- **Code (edited):** `src/App.tsx` (mount `<OrchestratorBridge />` inside the provider stack); `src/services/database/ProcessingQueueRepository.ts` (enqueue `task_type`/`model_version`, `getNextPendingByTaskType`, stale-`processing` recovery); `src/services/database/MediaFileRepository.ts` (stamp `processed_at`/`ai_model_version`/`ai_schema_version`, upsert-by-uri); `src/services/ml/ProcessingService.ts` (JSDoc-`@deprecated` the in-memory queue members; engine seam unchanged).
- **Contract:** `ProcessingResult` (change #2), `DiscoveredMedia`/`MediaChange` (discovery), and every model shape are consumed unchanged. `MediaDiscoveryService`, `SearchService.addToIndex`/`observeVisible`, and `BackgroundTaskService` public APIs are reused as-is.
- **Data:** no schema change (uses change #1 columns). New `media_files` rows get `processed_at`/`ai_model_version` on Tier-0 completion; new `processing_queue` rows get `task_type = "tier0_mlkit"`. Idempotent: dedupe by `uri`, skip already-processed files.
- **Dependencies:** none added — `react-native-background-actions`, `@react-native-camera-roll/camera-roll`, `react-native-fs`, `minisearch`, `react-native-mmkv`, and the native `MediaObserver` TurboModule are all already present. No new path alias (`@services/*`, `@components/*`, `@contexts/*`, `@models/*` already defined).
- **Conventions:** Biome (tabs, double quotes), `noExplicitAny: error`, all-static service classes (`noStaticOnlyClass: off`), strict TS (`noUnusedLocals`/`noUnusedParameters`/`noImplicitReturns`), legacy decorators.
- **Out of scope (later waves):** the Gemma/Tier-1 engine and its selection wiring, capability/thermal gating (change #5), model-version-aware bulk reprocessing (change #10), embeddings/semantic-search population, thumbnail generation, and any UI redesign of the processing/progress screens.
