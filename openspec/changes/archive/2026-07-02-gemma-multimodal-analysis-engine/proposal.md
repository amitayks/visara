## Why

Foundation #4 (`executorch-runtime-bootstrap`) proves the **Gemma-4 E2B multimodal** model *runs* on-device via `react-native-executorch`; foundation #2 (`analysis-engine-interface`) deliberately reserved a `tier1` bucket and an *additive* `ProcessingResult` extension point for exactly this ("no engine produces `caption`/`description`/`tags` yet"; "Result contract stays additive"); foundation #1 already ships the `media_files.caption/description/ai_model_version` columns and the `labels.source/type/model_version` provenance the enrichment must land in. What is still missing is the **producer**: a reusable Tier-1 `AnalysisEngine` that turns one image into a caption + description + open-vocabulary tags and maps them onto that schema with `source = "gemma"` provenance. This change adds that engine and registers it — and **nothing else runs it**: Tier-1 *selection*, drive, gating (`DeviceCapabilityService.canRunTier1()`, #5) and the drain wiring are #10's job. Building the engine is separable from deciding *when* to run it.

## What Changes

- **Add `GemmaMultimodalService`** — an all-static Tier-1 `AnalysisEngine` (matches `MlKitEngine`'s static shape, `src/services/ml/engines/MlKitEngine.ts`) with `descriptor = { id: "gemma", tier: "tier1", capabilities: ["caption", "description", "tags"] (POC: + "ocr"), modelVersion }`. Its `analyze(imageUri)`:
  - decodes the image to a **decodable `file://` JPEG via `ThumbnailService.getThumbnail`** (`src/services/media/ThumbnailService.ts:84`) — never a raw `content://` MediaStore URI (the ExecuTorch image decoder cannot read content URIs — see `executorch-runtime-bootstrap` proposal + `ExecutorchPocScreen.tsx:44-58`);
  - runs the model through the **imperative `LLMModule`** (`react-native-executorch`, `modules/natural_language_processing/LLMModule.ts` — `fromModelName(...)` + `generate(messages)` with a `user` message carrying `mediaPath`), **not the `useLLM` React hook**, because an `AnalysisEngine` is framework-agnostic and runs inside the no-React background drain (`OrchestratorService`). The hook and the module share the same native runtime/`LLMController`; #4's POC validated the hook path, this engine uses the module path;
  - loads `models.llm.gemma4_e2b_multimodal()` **once** (lazy single instance, reused across images — the model is a ~3.2 GB MLX / ~4.4 GB Vulkan `.pte`; per-`analyze` load is not viable);
  - parses the model output into caption + description + open-vocabulary tags (+ optional structured JSON), mapped **additively** onto `ProcessingResult` via a new optional `gemma?` field (the extension `analysis-engine-interface` reserved);
  - enforces a **per-image timeout** (race + `LLMModule.interrupt()`) and **resolves-never-rejects** — `success: false` + the contract's fallback sub-results on any error/timeout/unavailable runtime, byte-for-byte matching `MlKitEngine`'s envelope (`MlKitEngine.ts:38-58`).
- **Extend `ProcessingResult` additively** (`src/services/ml/ProcessingService.ts`) with an optional `gemma?: GemmaEnrichment` field. Existing consumers (`MediaFileRepository`, `SearchService`, `OrchestratorService`, UI) compile and run unchanged — this is the additive extension `analysis-engine-interface` explicitly sanctioned.
- **Register the engine in `EngineRegistry`** so `getById("gemma")` returns it and `getByTier("tier1")` includes it (mirrors the `MlKitEngine` seeding at `EngineRegistry.ts:27`). This **MODIFIES** the `analysis-engine-selection` scenario that asserts `getById("gemma")` returns `undefined` ("no Tier-1 engine is registered yet").
- **Add an additive persistence mapping** — `MediaFileRepository.applyGemmaEnrichment(mediaFile, gemma, provenance)` — that writes the enrichment onto the #1 schema: `caption`/`description`/`ai_model_version`/`ai_schema_version`/`processed_at` in one write (`media-enrichment-schema`), and `source = "gemma"` labels **replacing only `gemma` rows, leaving `mlkit` rows intact** (`label-provenance`), overwrite-in-place (never duplicating). The existing tier0 writers (`createWithProcessingResult`/`updateWithProcessingResult`, still hard-coding `source = "mlkit"`) are untouched. **This change does NOT call `applyGemmaEnrichment` from the orchestrator drain — it is the seam #10 invokes.**
- **POC-DEPENDENT (must be re-tuned once #4's on-device Gemma POC reports real latency / quality / output shape):** the prompt text; the output→fields parser and the optional structured-JSON schema; the exact `GemmaEnrichment` field set (tag confidence? `ocr` text? raw passthrough?) and therefore whether `"ocr"` is claimed in `capabilities`; the per-image timeout value; the `modelVersion` string; and `TIER1_SCHEMA_VERSION`.

## Capabilities

### New Capabilities
- `gemma-multimodal-analysis-engine`: the Tier-1 `AnalysisEngine` — its descriptor, its lazy single-instance load of `models.llm.gemma4_e2b_multimodal()` through the imperative `LLMModule` (framework-agnostic, not `useLLM`), its `ThumbnailService`-decoded `file://` input, its caption/description/tags production mapped additively onto `ProcessingResult`, its per-image timeout + interrupt fallback, its resolve-never-reject envelope, and its `EngineRegistry` registration — with the Tier-0 path and the orchestrator drain left untouched.
- `gemma-enrichment-persistence`: the additive `MediaFileRepository.applyGemmaEnrichment` write that maps a Gemma `ProcessingResult` onto the #1 schema — caption/description/provenance columns plus `source = "gemma"` labels that replace only `gemma` rows and leave `mlkit` rows intact, idempotent overwrite-in-place — provided as the seam #10 wires (not called by the drain here).

### Modified Capabilities
- `analysis-engine-selection`: the requirement **"A registry resolves engines by id and tier"** is updated — `EngineRegistry.getById("gemma")` now returns the Tier-1 `GemmaMultimodalService` and `getByTier("tier1")` includes it, superseding the wave-#2 scenario that asserted `getById("gemma")` resolves to `undefined`. No other requirement in that spec changes; the Tier-0 default, `getById("mlkit")`, and the `source = "mlkit"` tier0 write all stay as-is.

## Impact

- **New JS:** `src/services/ml/engines/GemmaMultimodalService.ts` (the engine). **Edited JS:** `src/services/ml/ProcessingService.ts` (additive `GemmaEnrichment` type + optional `gemma?` field on `ProcessingResult`); `src/services/ml/engines/EngineRegistry.ts` (seed the tier1 engine); `src/services/database/MediaFileRepository.ts` (additive `applyGemmaEnrichment` + a `TIER1_SCHEMA_VERSION` constant).
- **Dependencies:** none added — `react-native-executorch@0.9.2` + `react-native-executorch-bare-resource-fetcher` + `@dr.pogodin/react-native-fs` are already in `package.json:22,41-42`, and `initExecutorch(...)` is already wired in `index.js` (both by #4). This change assumes #4 is applied (its GO gate passed) so the runtime actually resolves at runtime; on a device where the native runtime is absent (`isAvailable === false`) the engine fails closed to `success: false`.
- **Schema:** none — #1 already added every column this writes (`schema.ts` v2: `media_files.caption/description/ai_model_version/ai_schema_version/processed_at`, `labels.source/type/model_version`). No migration.
- **Untouched (guaranteed):** the Tier-0 `MlKitEngine` pass and its `source = "mlkit"` writes; `OrchestratorService`'s drain (`processNext`/`maybeStartDrain` — no `tier1_gemma` enqueue, no Gemma selection, no `canRunTier1()` call added here); `SearchService` (indexing `caption`/`description`/`gemma` tags is a downstream #10/search concern — it currently indexes only `filename`/`labels`/`ocrText`); native builds (no native code; pure JS over the runtime #4 already integrated).
- **Conventions:** Biome (tabs, double quotes, `noExplicitAny: error`), strict TS, all-static services, `@services`/`@models`/`@shared-types` aliases. New/edited JS stays typecheck- and lint-clean.
- **Verify (baseline-relative):** `npm run typecheck` currently reports **8** pre-existing `TS6133` unused-symbol errors in 4 unrelated UI files; this change adds **zero** new typecheck errors (count stays 8), plus a Metro bundle check and a clean `npm run lint`.
- **Out of scope (belongs to #5/#10):** Tier-1 selection and the `tier1_gemma` drain; `canRunTier1()` gating; the version-aware SKIP that makes a re-run a no-op; search indexing of the new fields; model unload/eviction orchestration under thermal pressure.
